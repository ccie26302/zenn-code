日付: 2026-10-17。この文書と、課題(依頼文の全文・初期状態・判定・模範解答・惜しい誤答・別解)、出典の一覧、ハーネスを、予備試行の前に git にコミットする。予備試行のあとと本測定のあとに変えたことは、末尾の「変更履歴」に書く。

v1 からの変更: 外部レビュー2本(検証方法、安全と Google Cloud の操作)の指摘をすべて入れた。主な点は、問いの言い換え、Google Cloud の課題を5本から17本へ、権限をカスタムロールに、出口を HTTPS の中身を見る中継に、負の対照、ローカルの条件の固定、タイムアウトと打ち切りの規則、判定の別解での検証、頼んでいない変更と偽りの完了の記録、「使いこなせる」の判断規則の事前の決定。

## 問い(v3 で主眼を変更)

主眼: AI のサブスクの料金が上がったときの打ち手として、Qwen Code は Claude Code の代わりになるか。

1. できること: Claude Code の公開記事でみんながやっている種類の端末の作業(動画・音声・画像・文書・データ・ファイル・git・開発・クラウドの操作)を、Qwen Code はこなせるか。同じ課題・同じ隔離環境で Claude Code も流し、基準にする
2. 時間: 同じ作業に、Claude Code(サブスク)と比べて Qwen Code(従量課金のクラウド、手元のローカル)は何倍の時間がかかるか。全体の時間を、モデルの応答の待ち時間とそれ以外(ツールの実行など)に分ける
3. お金: 1つの作業あたりの費用。Q は usage と単価からの実費、L は API の費用ゼロ(電力は含めない)、C は Claude Code が出す API 換算の額(サブスクでは追加費用なし、利用上限を消費)。サブスクの月額(公式の料金を引用)と並べ、月に何回使うならどれが安いかを出す
4. 導入と使い方: Qwen Code の2つの構成の始め方
5. クラウドの操作(作業の種類の1つ): gcloud と Terraform で、使い捨てのプロジェクトのリソースを正しく作り、直し、片付けられるか。権限が足りないときに正直に止まれるか

出典は sources/claude_code_articles.md(47件)。Claude Code の結果は、記事の主張を確かめるものではなく、同じ条件で流した基準として扱う。

## S0 隔離と安全策

エージェントのコンテナ:
- colima 上の使い捨てコンテナで非 root。`--cap-drop ALL --security-opt no-new-privileges --pids-limit 1024 --memory 8g`。見せるのは作業フォルダ(`/work`)だけ
- `--internal` の Docker ネットワークにだけつなぐ。出られるのは中継のコンテナだけ。全課題で HTTPS_PROXY を中継に向け、外への接続の試みを記録する

中継(harness/proxy):
- 8080 モデル: `/vertex/` は `POST /v1/projects/<管理用>/locations/global/endpoints/openapi/chat/completions` だけを通し、本文に model が無いものは拒否。Authorization を推論権限だけの SA `qwen-model`(管理用のプロジェクト、カスタムロール qwenPredictOnly)のトークンに差し替える。`/ollama/` は `/v1/chat/completions`・`/api/chat`・`/api/tags`・`/api/show`・`/v1/models` だけ。ALLOW_MODELS で2つのモデルに限る
- 3128 Google Cloud への出口(mitmproxy、HTTPS を終端): Google Cloud の課題のときだけ開き(ctl/egress_mode)、それ以外は全部拒否。許可するホストは storage・run・asia-northeast1-run・iam・cloudresourcemanager・serviceusage・logging の完全一致。Authorization を `qwen-agent` のトークンに差し替え、`x-goog-user-project` を対象のプロジェクトにする。コンテナには `dummy` しか渡さない。拒否するもの: 署名付き URL と API キー、対象のプロジェクト以外への要求、接頭辞 `qg-` 以外のバケット、プロジェクトの外の人への付与と allUsers・allAuthenticatedUsers、保持ポリシーのロック、許可したイメージ(Google のサンプル hello、ダイジェスト固定の nginx)以外の Cloud Run、command・args の上書き、最小インスタンス1以上、最大インスタンス4以上、GPU、東京以外の地域、Cloud Run のジョブとワーカープール、SA の鍵・署名・setIamPolicy、プロジェクトの setIamPolicy、run・storage・logging・iam 以外の API の有効化(G06b では全部)。全要求と拒否の理由を logs/gcp_requests.jsonl に残す
- 9000 受け口

使い捨てのプロジェクト(組織に属さない):
- 新しく作り、請求先アカウントをつなぎ、予算のアラート(1,500円、50%と100%)
- 既定の Compute の SA に自動で付いた Editor を外した。Cloud Run の実行用には権限ゼロの SA `qwen-run-rt` を作り、`qwen-agent` にはこの SA の単位で serviceAccountUser だけを付けた
- `qwen-agent` と `qwen-judge` は管理用のプロジェクトに置き、対象のプロジェクトにはカスタムロールだけを付ける
  - qwenAgent: バケットとオブジェクトの作成・更新・削除・IAM(バケット単位)、Cloud Run のサービスの作成・更新・削除・読み取り、SA の作成・読み取り・更新・削除、API の一覧と利用、プロジェクトと IAM の読み取り、ログの読み取り。意図して外したもの: プロジェクトの setIamPolicy、SA の setIamPolicy と鍵、保持のロック、Cloud Run の setIamPolicy・ジョブ・ワーカープール
  - qwenJudge: 読み取りだけ(バケット・IAM・Cloud Run・SA・API・ログ)
- 負の対照(測定前に実施済み、harness/negcontrol_result_1.csv): qwen-agent のトークンで、やってよい5つの操作が通り、やってはいけない15の操作(接頭辞外のバケット、公開、外部の人への付与、プロジェクトの IAM、SA の鍵、SA の IAM、Compute の有効化、任意のイメージ、最小インスタンス、別の地域、ジョブ、別のプロジェクト、外のサイト、署名付き URL)がすべて止まることを確かめた
- 試行ごとに、試行の前に基準(harness/base)と一致することを確かめ(一致しなければ止める)、判定のあとに基準との差分を消して戻す(バケット・Cloud Run・ジョブ・SA・API・プロジェクトと qwen-run-rt の IAM)
- 監視: 試行ごとに、片付けの前の基準との差分(gcp_diff_before_restore.txt)を記録する
- 判定: qwen-judge のトークンで実際の状態を読む。Terraform の判定は、エージェントの .tf と state だけを別のフォルダに写し、local の backend を強制し、イメージのプロバイダ(ミラー)で plan する。state はエージェントが書き換えられるので、実際のリソースも API で確かめる

## 条件と打ち切り

- エージェント: Qwen Code 0.25.2、`--approval-mode yolo`、ヘッドレス、`-o stream-json`、設定ファイルは置かない(既定のまま)
- 反復: すべての構成で、全課題を各3回(v3 で G・T 群の Q の5回を3回に変更)
- 順序: 課題と回をシード固定でシャッフル。Q と L は別々に流す(L は手元の GPU を使うので並列数1、Q も同じプロジェクトを使うので並列数1)
- タイムアウト: Q は課題ごとの timeout_sec(20〜40分)、L はその3倍(上限60分)。時間切れは不合格に数え、別の型として報告する
- 費用の打ち切り: Q のモデルの費用(usage と単価からの試算)が累計30ドルを超えたら止める。Google Cloud のリソースは予算のアラートで見る
- 時間の打ち切り: L が全体で72時間を超えそうなら、L の M・D 群 → L の前作の課題の順に反復を減らす。G・T 群は削らない
- 予備試行: 各課題を各構成で1回。直してよいのは、ハーネスの不具合と課題文のあいまいさだけ。直したら、変更の前と後の両方の判定を報告する。予備試行の結果は本測定に数えない

1. G・T 群の課題ごとの判定(3/3 を「できる」(v3 で反復を3回にそろえた)、1〜(n−1)/n を「不安定」、0/n を「できない」)
