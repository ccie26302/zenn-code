# 新しい基本ロール Admin / Writer / Reader の検証計画 v2(事前登録)

日付: 2026-10-30。この文書は測定の前に git にコミットする。測定のあとに変えた点は末尾の「変更履歴」に書く。

## 記事の主張(仮)

1. Owner / Editor / Viewer の後継として Admin / Writer / Reader が GA になった。条件(IAM Conditions)が付けられるのが最大の違いで、期限付きや対象を絞った「基本ロール」が初めて作れる
2. ただし、名前を置き換えるだけの移行は安全ではない。権限の中身が一致しないうえ、Cloud Storage の簡易値と BigQuery の特殊グループ経由のアクセスは新ロールに付かない。しかもそれらは既定の設定で作ったリソースに最初から入っている可能性がある。旧ロールで動いていたものが、黙って止まる場所がある
3. どこが変わるかを機械で洗い出し、止まらない手順(コマンド)で置き換える。持ち帰れるのは、差分の出し方、条件付きの付与、影響の洗い出しスクリプト、移行の手順

主張は結果で変える。差が無ければ「名前を変えるだけで済む」と書く。

## 一次情報(測定前に確認済み)

- IAM Roles overview(https://docs.cloud.google.com/iam/docs/roles-overview)
  - 本番では基本ロールを付けない。付けるなら、テストや検証の環境では Admin / Writer / Reader を勧める(条件が使えるため)
  - 旧ロールには条件を付けられない
  - Cloud Storage の簡易値と BigQuery の特殊グループのメンバーシップは、Admin / Writer / Reader の持ち主には権限を与えない
  - Writer は、すべてのサービスのすべての操作ができるわけではない
  - Admin は Writer に加えて、Compute Engine のタグの紐付け、プロジェクトのロールと権限の管理、課金の設定などができる。支払い情報の変更と拒否ポリシーの作成はできない。Owner も同じ
  - コンソールからは Admin / Writer / Reader を付けられない(API か gcloud を使う)。Privileged Access Manager の付与対象にはできる
  - 旧ロールは、自動の処理で今も使われている(例: プロジェクトの作成者には Owner が付く)
  - 組織の外のユーザーに、または組織に属さないプロジェクトで Owner を付けるには、コンソールが必要(招待と承諾)
- BigQuery の基本ロール(https://docs.cloud.google.com/bigquery/docs/access-control-basic-roles): データセットを作ると、旧ロールに対応するエントリが既定で入る(Viewer→READER、Editor→WRITER、Owner→OWNER)。実測で確かめる
- Cloud Storage の簡易値(https://docs.cloud.google.com/storage/docs/access-control/iam、https://docs.cloud.google.com/storage/docs/access-control/lists)
  - バケットの IAM のメンバーでは `projectOwner:<ID>` / `projectEditor:<ID>` / `projectViewer:<ID>`
  - ACL のエンティティでは `project-owners-<番号>` / `project-editors-<番号>` / `project-viewers-<番号>`
  - 均一なバケットレベルのアクセスは、有効にして90日たつと元に戻せない
- IAM の反映時間(https://docs.cloud.google.com/iam/docs/access-change-propagation): 通常2分程度、7分以上かかることもある
- 手元の観察(本測定ではない): `gcloud iam roles describe` の権限数が、呼ぶたびに変わる。Admin は 13,992 と 14,153 が混じった(5回中1回)。Owner は 13,927 のほか、別の時刻に 14,088 を見た。etag はいつも `AA==`

## 環境

- 使い捨てのプロジェクト `br-verify-<日付>`(組織なし、個人の請求先)。予算 1,000 円(50/90/100% で通知)
- 試験用の主体は、そのプロジェクトのサービスアカウント(SA)で、ロールごとに1つ作る: none / viewer / reader / editor / writer / owner / admin
- 自分のアカウントには、各 SA の `roles/iam.serviceAccountTokenCreator` だけを付ける。なりすましでアクセストークンを取り、操作は curl で REST を直接叩く(gcloud の起動時間と quota_project の影響を除くため)
- `x-goog-user-project` は付けない(付けると serviceusage の権限で落ちるため)。付けた場合の差は E3 の付録として1回だけ確かめる
- SA は測定の前に作り、陽性対照のプローブが10回連続で期待どおりになり、かつ作成から1時間以上たってから測定を始める
- gcloud のバージョンを記録する(587.0.0)。生の応答はすべて JSONL で `data/` に残す。`run.sh` と `REPRODUCE.md` で再現できるようにする

## 判定の共通ルール

- 「拒否」と数えるのは、HTTP 403 で、理由(ErrorInfo の reason、またはメッセージ)が権限の不足を示すものだけ。409(既に存在)、404、API が無効、クォータの不足は「判定不能」として別に数える
- 「成功」は 2xx で、かつ読み戻しで状態が変わったことを確かめたもの(作成なら get で存在する、書き込みなら読み戻して一致する)
- 作成系の操作は、回ごとに一意の名前を使う
- 伝播: 付与したあとは、その SA で陽性対照のプローブ(付与によって通るようになる操作)が5回連続で通るまで待つ。外したあとは、5回連続で拒否されるまで待つ。待った時間も記録する(E5 の補助データになる)

## 実験

### E0 ロール定義の揺れ(観察)
- 6ロールそれぞれを、REST の roles.get と gcloud の2経路で、30秒おきに50回ずつ取る。日を変えて2回行う
- 記録: 時刻、経路、権限数、権限の集合のハッシュ。異なる集合が出たら、その中身を保存する
- 集合が1種類なら「揺れなし」。2種類以上なら、出現の割合と差の中身を報告する。原因は断定しない(展開中の可能性として書く)
- E1 の比較には最も多く出た集合を使い、揺れた分は別に示す

### E1 権限の静的な差分
- 3組(Owner↔Admin、Editor↔Writer、Viewer↔Reader)について、片方だけにある権限を全部出し、サービスごとに集計する
- 危険度の高い権限のリストを先に決め、6ロールのどれに入っているかを表にする
  - IAM: `resourcemanager.projects.setIamPolicy`、`iam.serviceAccounts.setIamPolicy`、`storage.buckets.setIamPolicy`、`bigquery.datasets.setIamPolicy`、`iam.roles.create`、`iam.roles.update`、`iam.denypolicies.create`
  - なりすまし: `iam.serviceAccounts.actAs`、`iam.serviceAccounts.getAccessToken`、`iam.serviceAccounts.signBlob`、`iam.serviceAccounts.signJwt`、`iam.serviceAccounts.implicitDelegation`
  - 長く使える鍵: `iam.serviceAccountKeys.create`、`storage.hmacKeys.create`、`apikeys.keys.create`
  - 秘密情報: `secretmanager.versions.access`
  - 課金: `billing.resourceAssociations.create`、`resourcemanager.projects.createBillingAssignment`
  - 監査: `logging.sinks.delete`、`logging.buckets.update`、`logging.buckets.delete`
- ドキュメントの主張(拒否ポリシーの作成と支払い情報の変更ができない)を、Admin と Owner の両方で権限から確かめる

### E2 付与のしかたの違い
- 条件: 6ロールそれぞれに、同じ期限の条件を付けて付与を試みる。旧ロールは拒否され、新ロールは通ると予想している。エラー文を記録する
- コンソール: 新ロールが付与の画面の候補に出るか(読み取りの確認だけ。画面写真を残す)
- Owner / Admin を SA に、gcloud で付けられるか(組織なしのプロジェクト)
- (ユーザーの了承が要る。了承が無ければやらない) 自分の別の Google アカウントに Owner と Admin を gcloud で付けたとき、招待と承諾が要るかどうか。要らない場合は、承諾前に権限が効くかも確かめ、すぐに外す
- 期限切れの条件付きバインディングが、ポリシーに残るかどうか

### E3 実際の操作で効くかどうか(主要評価項目)
- 操作の一覧と、操作ごとに必要な権限(複数のリソースにまたがるものは全部)を、測定の前に `tasks/e3_ops.yaml` に固定する。約30操作。各ロールの SA で、各操作を3回行う。順序はシードを固定してシャッフルする
- 操作の群
  - (a) E1 の差分から選んだ操作。差分のあるサービスごとに最低1つ選ぶ
  - (b) 旧ロールの「おまけ」経路。リソースは次の条件で作る
    - BigQuery: `bq mk` の既定でデータセットを作る(既定で特殊グループが入るかを、作った直後に記録する)。テーブルの読み取り、書き込み、データセットの更新
    - Storage(均一アクセスあり): gcloud の既定でバケットを作り、バケットの IAM ポリシーを記録する(簡易値が入っているか)。オブジェクトの読み書き。比較として、簡易値をわざと付けた版も作る
    - Storage(均一アクセスなし、細かい ACL): 既定のオブジェクト ACL のまま置いたオブジェクトと、`project-editors-<番号>` などだけに許可したオブジェクト
    - 予想: 旧ロールは通り、新ロールは止まる。ただし新ロール側に storage や bigquery の権限が直接入っていれば通る。どちらなのかを実測で決める
  - (b') 「おまけ」を外して締め出したリソース(v2.1 で追加)
    - バケット: ACL とバケットの IAM から `project-viewers-<番号>` / `projectViewer:<ID>`(および editors)を外し、オーナーだけが触れる状態にする。均一アクセスあり・なしの両方
    - データセット: access から projectReaders / projectWriters を外す
    - 予想: 旧ロールは止まり、新ロールは通る(新ロールはプロジェクトの単位で storage.objects.* と bigquery.tables.* を持つため)。通った場合は「移行で締め出しが外れる(権限の拡大)」として報告する
  - (c) よくある開発作業: バケットの作成、Pub/Sub のトピック作成と発行、Secret の作成と読み出し、Cloud Run へのデプロイ(公開イメージ、最小の設定。run と actAs と必要な API の権限)、SA キーの作成(作成できたらすぐに消す)、別の SA の actAs、プロジェクトの IAM ポリシーの変更、ログのシンクの削除
  - (d) 対照: ロールなしの SA は全部拒否される(陰性対照)。自分(Owner)は全部通る(陽性対照)
- 予測との一致: 各操作の前に、必要な権限について `testIamPermissions` を問い合わせ、予測と実際の一致を数える。一致率は経路ごと((a)(b)(c))に分けて出す。(b) は ACL や特殊グループが testIamPermissions に反映されないことが予想されるので、そのこと自体を結果として書く
- 不一致の操作は、Policy Troubleshooter(使える範囲で)でも判定し、原因を個別に書く
- 3回すべて同じ結果なら確定とする。割れたら「不安定」とし、もう3回だけ追加で行う

### E4 条件付きの基本ロールが実際にどう効くか
- 期限: Writer を、今から10分の条件付きで付ける。期限の前後2分を、2秒おきに同じ操作(curl)で試す。サーバの Date ヘッダーと期限の差を記録する。5回
- 対象の絞り込み: Writer を `resource.name.startsWith(...)` の条件付きで付け、名前が合うものと合わないものを試す。対象は、条件に対応するサービス(Storage、Secret Manager、Compute)と、対応しないサービス(Pub/Sub、BigQuery など)。対応しないサービスで何が起きるかは、ドキュメントに書かれていないので両側を実測する。`resource.service != "..." ||` で逃がす書き方とも比べる
- 一覧系の操作(親のリソースで評価される操作)が、条件で止まるかどうかも確かめる
- 陽性対照: 条件なしの Writer では、同じ操作が通ること

### E5 置き換えの順番と止まる時間
- 旧→新の置き換えを3通りで行う。トークンを先に取っておき、代表の操作を curl で0.5秒おきに叩き、拒否された時間をサーバ時刻で記録する。各20回。中央値と最大値を出す
  - 先に外す: Editor を外してから Writer を付ける
  - 先に足す: Writer を付けてから Editor を外す
  - 一括: 1回の setIamPolicy でまとめて入れ替える
- 代表の操作は2つ選ぶ。(c) の一般的な操作から1つと、(b) の「おまけ」経路から1つ。(b) は、どの方式でも止まり続けるはず。止まらない移行のために、データセットやバケットに個別の許可を足す手順を示し、足したあとに通ることも確かめる

### E6 影響の洗い出しスクリプト(持ち帰り用)
- 入力はプロジェクト ID。次の4つを出す
  - 旧ロールの付与の一覧と、置き換えの案
  - 既定 SA への自動付与で、置き換えないもの
  - 簡易値や特殊グループに頼っているバケット、オブジェクトの ACL、データセット
  - E1 の差分のうち、そのプロジェクトで有効になっている API に関係するもの
- 評価は2段階
  - 乱数のシードで別の試験プロジェクトにリソースを植える。経路のあるものと、似ているが影響のない囮を混ぜる。正解の表は封をしたまま(ハッシュだけを先に記録)流す
  - gcloud、bq、コンソールの既定で作っただけのリソースでも流す
- 正解の定義: 「E3 と同じ方法で、旧ロールの SA が通り、新ロールの SA で止まったもの」。スクリプトの出力と比べて、見逃しの数と誤検知の数を出す
- Policy Simulator が組織なしのプロジェクトで使えるかを試し、使えた場合は Editor → Writer の置き換えをシミュレーションして E3 と比べる。使えなければ、使えなかったと書く

### E7 周辺の見え方(記述)
- 自動付与: 組織なしのプロジェクトで、Compute のデフォルト SA や Google の API サービスエージェント(cloudservices)に Editor が付くかを記録する
- Cloud Asset Inventory の searchAllIamPolicies(プロジェクトを範囲にする)で、新ロールの付与と、データセットの特殊グループがどう見えるか
- 監査ログ(Admin Activity)の bindingDeltas に、ロール名と条件がどう記録されるか
- Privileged Access Manager: roles/writer と roles/editor の両方で、プロジェクトを範囲にした資格の作成を試す(料金を確認してから)

## 主要評価項目(先に固定)

1. E3(b)(b'): 既定で作ったリソースと、締め出したリソースのそれぞれで、旧ロールと新ロールの結果が食い違う操作の数(ロールの組ごと、向き別: 新で止まる/新で広がる)
2. E3 全体: 7主体 × 約30操作の成功/拒否/判定不能の表と、testIamPermissions の予測との経路ごとの一致率
3. E5: 置き換えの方式ごとの、止まった時間(秒。20回の中央値と最大値)
4. E6: 洗い出しスクリプトの見逃しの数と誤検知の数(植え込み版と、既定で作った版)

E0、E1、E2、E4、E7 は記述(探索的)として扱う。

## やらないこと

- 組織ポリシー、拒否ポリシー、フォルダの階層での付与(組織が無いため)。記事では「組織がある場合の確認事項」として、一次情報だけで触れる
- IAM Recommender(観察期間が足りないため)
- 本番のプロジェクトでの試行。既存のプロジェクトの IAM には触れない
- 他人のアカウントへの付与

## 費用と片付け

- 予算 1,000 円。Cloud Run、BigQuery、Storage、Pub/Sub、Secret Manager は無料枠の範囲に収まる見込み。PAM は料金を確認してから
- 作った SA キーと HMAC キーは、作成の成否を記録したらすぐに消す。キーの値は保存しない
- 記事の下書きを push したら、プロジェクトごと削除する
