## アラートの計測メモ
- trial 1: ポリシー作成(03:04 頃)の約3分後に4つの操作(03:07:17〜25)。発火したのは t1: key_create だけ(03:08:22)。
  public_run / public_gcs / invoker_disabled は、フィルタは監査ログに一致していた(gcloud logging read で確認)のに、13分待っても発火しなかった。
  ポリシー作成から約15分後(03:18:59〜03:19:05)に同じ3つの操作をやり直すと、3つとも 03:19:39 に新しいインシデントとして通知された。
  => 作ったばかりのログベースのアラートは、すぐには効かないことがある。trial 2・3 は作成から15分以上おいて測った。
- 同じ時刻に、既存の(古いフィルタの)ポリシー "SA key created" と "Public grant" も新しいインシデントとして 03:08:22 に通知。
  "Cloud Run invoker IAM check disabled" は 01:45:42 に開いたインシデントへの再通知だった。
- 旧データ(alerts_reopened_incidents.csv)の 23〜37秒は、開いたままのインシデントへの再通知を測っていた(incident_id が同じ、started_at 01:45:42)。
- 旧スクリプトは Pub/Sub の data を標準の Base64 として読んでいた。data は URL-safe Base64 なので、'-' '_' を含むと途中から壊れていた。
- trial 2: 作成から16分後に操作(03:37:23〜31)。4つとも新しいインシデントとして 03:38:36 に通知。
- trial 3 は無効: trial 3 用のポリシーを trial 2 の前に作っていたため、trial 2 の操作で先に発火し(03:38:36)、
  trial 3 の操作(03:39:3x)では、通知が1件も届かなかった(5分の通知間隔の制限に入ったため)。
  以降は1回分のポリシーだけを作って測る(trial 4)。
- trial 1 の key_create は作成3分後の操作、他の3つは作成15分後の操作。
- trial 4: 作成(03:51:31)から16分後に操作(04:08:04〜13)。4つとも新しいインシデントとして 04:09:02 に通知(49〜58秒)。
- 記事の「1回目・2回目・3回目」= trial 1・2・4。
- 記事の秒数は data/alert_compute.py で alert_audit_events.csv と alert_messages.csv から出し直せる(alerts.csv と一致)。
- 計測の終点は Pub/Sub の publishTime。メールなどで人に届くまではさらにかかる。
